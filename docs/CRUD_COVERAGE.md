# Application CRUD coverage

This document defines the supported create/read/update/delete behavior for each user-facing data area. Provider-owned records are changed through their provider APIs; they are not treated as editable local replicas.

## CRUD matrix

| Data area | Create | Read | Update | Delete / archive |
| --- | --- | --- | --- | --- |
| Account profile | Email/password signup or Google signup | Session/profile and complete account export | Display name, timezone, briefing and approval preferences | Permanently delete account and cascaded app data after password or Google identity re-verification; Google token revocation is best-effort |
| Tasks | Create a local task or approve an email-derived task proposal | Task list, briefing and schedule views | Title, description, due date, priority and status | Soft-cancel; task history and source references are retained |
| Google Calendar | Create a provider event after explicit confirmation | Date-range sync from the primary calendar | Update the Google event after rechecking availability and event version | Cancel the Google event (provider cancellation, not a local-only delete) |
| Gmail inbound messages | Gmail delivers the message; the agent records a tenant-scoped reference | Full email body and attachments metadata fetched from Gmail on demand | Mark read/unread, star/unstar, archive/move to inbox; update Gmail labels | Move to Trash and restore. Permanent deletion is not exposed |
| Outbound email drafts | Compose and save a local draft | Outbound draft list and inbound reply composer | Edit recipient, subject, cc and body; approve the exact content | Cancel an unsent draft; send requires separate explicit confirmation |
| Conversations | Start a conversation and create its messages through chat | Search/list/open saved conversations and transcript | Rename conversation | Delete conversation and its child messages together |
| Notifications | Created by app events | List notification feed | Mark one or all read | Delete an individual item or clear read items |
| Daily briefings | Generated by the briefing service | Saved briefing list and notification center | Mark read | Delete an individual briefing or clear read briefings |
| Follow-ups | Generated from source email/calendar evidence | Overview and briefing | Reopen or dismiss | Dismiss is reversible; generated evidence is not edited |
| Automation rules | Create a rule | List active rules | Change name, action, mode, conditions and enabled state | Delete a rule |
| Proposed actions and audit | Propose an action; the system records execution events | Pending and completed action history; audit history | Approve/reject through the action state machine | Action and audit history are retained; arbitrary edits/deletes are intentionally unsupported |
| Google connection | OAuth connect | Connection status, scopes and provider health checks | Reconnect to refresh token/scopes | Revoke access and remove the app's stored integration record |

## Provider-owned integration data

### Gmail

The email inbox stores message IDs and processing metadata, not editable copies of Gmail message bodies. Opening a message fetches its current content from the signed-in user's Google account. Gmail mailbox actions call the Gmail API.

The app requests \`gmail.modify\` for mailbox management. Existing connections must reconnect after this change. The interface exposes read/unread, star/unstar, archive/move-to-inbox, Trash and restore-from-Trash. A message is moved to Trash rather than permanently deleted.

Outbound email is a separate local-draft lifecycle. The exact saved draft must be approved before the Send control becomes available. Sending requires a second explicit confirmation and the \`gmail.send\` scope.

### Google Calendar

Calendar event creation, editing and cancellation use the Google Calendar API. The app mirrors events into the unified schedule for display and conflict handling, but provider mutations remain authoritative. The app requires calendar event permission and rechecks availability before an update; event IDs and etags are used to avoid editing a stale version.

## Retained history and derived records

CRUD does not mean every table should permit arbitrary hard deletion. The following are intentionally lifecycle-managed:

- Tasks use soft-cancel so history and links remain consistent.
- Action records follow approval/execution states and are retained.
- Audit events are append-only.
- Individual chat messages remain part of their conversation transcript; deleting the conversation deletes the transcript as a unit.
- Follow-ups are derived from email/calendar evidence, so dismiss/restore is the supported user action.

These constraints preserve idempotency, auditability and the relationship to external provider data.

## Validation

CI now runs:

\`\`\`sh
npm run test:crud-surface
npm run test:google-data-crud
npm run test:sidebar-routes
npm run verify:javascript
npm run build
npm run test:e2e
\`\`\`

The CRUD surface test checks the expected API method coverage and verifies that controls are mounted in the relevant client pages. The Gmail action test validates the provider label payloads. CI uses a seeded PostgreSQL database and deterministic provider mocks; it does not modify a live Google account. Complete the manual dedicated-test-account acceptance in \`docs/sidebar-workflow-audit.md\` before treating the live provider workflows as verified.
